# Этап миграции Android-клиента WaysGram на собственный API

## Что добавлено в этом этапе

waysgram/WaysGramApiClient.java — отдельный REST-транспорт на стандартном HttpURLConnection без Retrofit/OkHttp и без изменений в ConnectionsManager. Класс переносится в исходники исходного Android-клиента при запуске waysgram/apply_android_patch.py.

waysgram/WaysGramSessionStore.java — отдельное хранилище пользовательского access token. Токен шифруется AES/GCM ключом Android Keystore, который не экспортируется из устройства. Это хранилище не использует Telegram UserConfig и не меняет Telegram-сессии.

waysgram/WaysGramAuthRepository.java — отдельный репозиторий авторизации: запрашивает OTP только у backend WaysGram, проверяет код, сохраняет выданный backend-токен, проверяет профиль через /api/me, восстанавливает сессию и отзывает её при выходе. Он не создаёт фиктивный TLRPC.User и не вызывает Telegram auth.sendCode/auth.signIn.

waysgram/WaysGramModels.java содержит отдельные модели WaysGram для пользователей, диалогов, сообщений, каналов, постов и подарков. waysgram/WaysGramMessagingRepository.java использует эти модели и защищённую сессию для чтения списка диалогов, поиска пользователей, личных сообщений, каналов, публикаций и каталога подарков. В новых репозиториях нет зависимости от TLRPC или ConnectionsManager.

Транспорт предоставляет асинхронные методы для существующих серверных маршрутов:

- конфигурация backend и получение собственного OTP;
- проверка OTP WaysGram и завершение сессии;
- текущий профиль и поиск пользователей;
- список недавних личных диалогов и сообщения между пользователями;
- отправка личных сообщений;
- список каналов, чтение канала и ленты;
- публикация сообщения в канал;
- каталог подарков.

Ответы и ошибки возвращаются на Android UI thread через callback. В сетевом потоке задаются connect/read timeout, отключён HTTP cache, размер ответа ограничен и запрещено автоматическое следование HTTP-редиректам. Токен передаётся только заголовком Authorization: Bearer ...; клиент не пишет его в логи и не сохраняет самостоятельно.

## Политика адреса API

Для удалённого сервера принимается только HTTPS. HTTP разрешён только для loopback/dev адресов: localhost, 127.0.0.1, ::1 и 10.0.2.2. В Android-приложение нельзя вшивать production URL с паролем, SMS-секретами или административным токеном.

Конструктор WaysGramApiClient(Context) читает адрес из той же локальной настройки waysgram_admin_panel/api_url, которую сохраняет уже существующая «Админ-панель WaysGram». Таким образом, для будущего входа/чатов не требуется отдельный экран настройки адреса VDS.

## Важное ограничение

REST-транспорт, репозитории авторизации и данных, типизированные модели и Keystore-хранилище добавлены в исходники. Они пока не привязаны к виджетам LoginActivity, DialogsActivity или ChatActivity. Оригинальная авторизация и переписки продолжают работать через прежние Telegram MTProto-вызовы. Само наличие репозитория не означает, что экран входа уже переключён на WaysGram. Это сделано намеренно: после OTP нельзя переводить пользователя в оригинальный главный экран до миграции его хранилища диалогов и моделей данных — иначе можно показать пустой или некорректный Telegram-интерфейс.

Не смешивать:
- OTP, выпущенный собственным сервером WaysGram, и код входа Telegram;
- собственные Ways Stars/подарки и настоящие Telegram Stars/подарки;
- идентификаторы пользователей WaysGram и Telegram ID;
- личные чаты WaysGram и MTProto диалоги.

## Последовательность дальнейшей интеграции

1. Авторизация. Подключить WaysGramAuthRepository к существующему экрану входа, сохранив визуальные компоненты. После verifyCode сохранять токен через WaysGramSessionStore, а при выходе отправлять /api/auth/logout и очищать хранилище. Переходить в главный интерфейс после этого можно только после подключения основного WaysGram data layer.
2. Профиль и поиск. Создавать модели пользователя WaysGram отдельно от TLRPC.User; подключить профиль и поиск к /api/me и /api/users.
3. Диалоги и переписка. Подключить DialogsActivity к /api/conversations, а ChatActivity к /api/messages; обеспечить стабильное отображение серверных идентификаторов и локальный кэш.
4. Каналы и подарки. Подключить экраны к private API; права публикации остаются серверной проверкой.
5. Медиа, уведомления, синхронизация. Добавить object storage, upload/download API, push gateway и WebSocket/другой механизм событий. Только после этого можно мигрировать вложения и realtime-поведение.
6. Звонки и E2EE. Это отдельные подсистемы, они не появляются от добавления REST endpoints.

Каждый этап должен проходить сборку, backend smoke tests и отдельную интеграционную проверку до переключения соответствующего экрана. Не удалять MTProto из проекта целиком до того, как все нужные экраны и сценарии успешно заменены.
